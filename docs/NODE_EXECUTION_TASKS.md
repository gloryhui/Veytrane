## 1. 工作方式

### 2026-10-20 用户执行调整（优先于下述原工作流程）

用户已明确授权 Codex 接手全部实施，开启 Goal 持续推进，并要求优先完成代码、测试与回归后置，完成后提交推送。当前使用 `codex/node-implementation` 作为分任务提交的累计实施分支，基于已核实的 T00 与审核记录；不把尚未合并的依赖冒充 main 基线。允许按规格依赖继续实施草稿，测试/合并门槛保留为验收门槛，不再阻止这一轮代码编写。协议、权限、持久化恢复及 IPC 仍先写明确规格，再实施。

前一轮只执行格式、语法、编译及静态检查。当时不运行测试、回归或真实设备验收。各任务报告分别标明“已实现、静态检查通过、待测试”，不能用本轮结果关闭缺陷或宣告阶段已验收。原审核报告保留其对应 SHA 的历史结论。未授权合并 main、部署服务器或关闭 Issue。Codex 实质开发提交按用户共同作者规则署名。

用户随后明确要求“继续跑测试和回归，优先验证三个缺陷和新 Agent 的完整流程，发现问题直接修复，本机能做的全部完成后提交并推送”。该指令取代测试后置要求。当前已执行 Windows 与本机 Ubuntu WSL 的进程、浏览器、全量及宿主回归，修复所发现问题；详细命令、准确代码 SHA、结果和未验范围见 [本机回归](task-reports/LOCAL_REGRESSION.md)。本轮自检不冒称独立审核，不自动合并、部署或关闭 Issue。

进度与待验收清单见 [实施进度](task-reports/IMPLEMENTATION_STATUS.md)。

GPT 负责冻结规格、派发任务和独立审核；DeepSeek 负责已解锁任务的实现、必要自检和任务分支提交。实际模型由运行环境选择，本文及 Prompt 不能自行切换模型，也不证明该型号已接入。启动前确认运行环境中的型号，不得静默用其他型号替代。

每次只执行一张卡，提交推送后停止。依赖任务必须有 GPT 的审核通过记录；“已提交”“自检通过”都不代表审核通过。审核以准确的提交 SHA 为对象，有新代码提交即需重新审核相关差异。依赖任务只有合并到主线后才能作为后续任务的默认基线。

任务分两类：

- **工作卡**：DeepSeek 实施，GPT 审核；边界不清时提交问题和证据，不自行扩大设计。
- **规格卡**：GPT 先写接口、状态机、失败行为和验收向量并审核定稿，随后解锁工作卡。后续阶段尚未确定的物理路径、类型和命令必须在规格卡中补齐，不能将方向性设计冒充可直接编码的规格。

当前仅 T00 可直接领取。后续任务的依赖、阶段退出条件和审核记录都满足后才能解锁。本文没有授权一次执行完整迁移、自动合并、部署服务器或关闭 GitHub Issue。

### 1.1 拉取最新代码与隔离分支

每次新任务必须先执行并记录：

```sh
git status --short
git branch --show-current
git fetch origin
```

工作区干净且处于 `main` 时：

```sh
git pull --ff-only origin main
git rev-parse HEAD
git switch -c work/node-t00-baseline
```

分支名随任务替换为 `work/node-tNN-简短英文主题`。不在 `main` 实现工作卡。若当前不是 `main`，先核对当前分支用途；干净且无需要保留的独有工作时再切换 `main` 拉取。遇到脏工作区、分支分叉或同名任务分支已有工作时，报告状态或使用独立 worktree，不得 reset、强制切换、自动 stash、覆盖文件或丢弃他人工作。续做任务保留原分支，并核对远端及审核所指 SHA，不能重新开始覆盖提交。

设计基线仅供历史对照，实际修改以本次拉取的最新 `origin/main` 为准。若上游已经实现或改写任务目标，先报告差异与验证结果，不能重复修复。历史缺陷复现可用独立临时 worktree，不能把主工作区退回旧代码。

### 1.2 范围、提交和停止条件

- 每张工作卡使用一个任务分支；通常一个实现提交，返修追加提交。需要明显跨越两个目标时先拆卡。
- 允许路径包括卡中指定文件、对应专项测试及该卡报告；未列出的生产文件、依赖升级、协议编码、数据 schema 或 CI 改动需先由 GPT 更新任务规格。
- 不顺手格式化无关文件，不批量提交工作区中非本任务改动，不在修复卡中完成后续架构重构。
- 同一失败原因最多两轮针对性修正；仍失败则记录已尝试内容、原始错误和阻塞条件，停止扩大搜索或反复执行命令。检查超时也必须有结果摘要。
- 失败代码不得作为“完成”提交。确需保留诊断进度时可提交为明确的未完成草稿，报告和审核状态均保持阻塞，不能解锁依赖任务。
- 仅提交任务涉及的文件，检查 staged diff 后推送任务分支；禁止直接推送实现到 `main`、强推、重写历史和自行合并。主线集成由 GPT 在明确授权下处理。
- 保留有效 Git Author/Committer。仅 DeepSeek 参与的代码不添加 Codex 共同作者；若 GPT 后续实质参与代码或测试，按用户规则在对应新提交末尾加入一次 `Co-authored-by: Codex <codex@openai.com>`。仅审核或执行 Git 命令不冒认开发贡献。

## 2. 自检、证据与审核

### 2.1 检查档位

卡中使用以下检查档位，专项验收始终必做。命令来自当前 Cargo 组织，目录拆分后由规格卡更新，不能套用失效命令后谎报成功。

| 档位 | 必做检查 | 使用范围 |
| --- | --- | --- |
| D | `git diff --check`；本次 Markdown 相对链接、任务依赖、命令和验收编号核对 | 文档/规格/报告 |
| W | D；真实浏览器执行卡中交互并记录前后状态；相关后端有修改时追加 R | Web 草稿 |
| R | D；`cargo fmt --all -- --check`；`cargo check --locked --all-targets`；`cargo clippy --locked --all-targets -- -D warnings`；卡中指定测试与故障场景 | 默认 Rust 核心 |
| G | R；`cargo check --locked --features gui --bin p2p-desktop`；`cargo clippy --locked --features gui --all-targets -- -D warnings`；受影响 GUI 库测试 | GUI 或共享核心抽取 |
| I | D；默认全目标测试、GUI 库测试及适用 CI/进程验收；记录平台和构建 SHA | 阶段集成 |

常用测试命令：

```sh
cargo test --locked --lib admin:: -- --nocapture
cargo test --locked --lib tunnel:: -- --nocapture
cargo test --locked --all-targets --no-fail-fast
cargo test --locked --features gui --lib --no-fail-fast
```

新专项测试在报告中写完整、可重跑命令。必须核对实际执行的测试数量；筛选到 0 个测试不算通过。新增回归优先复用已有测试基础，不为简单文档或表单修改引入大型框架。缺陷卡需要证据证明原版本失败、修复版本通过；浏览器问题允许可重复的真实操作步骤和截图，无需为测试而建立整套 UI 工程。

不要求每个小任务重复运行所有平台与公网测试。P1–P5 每阶段出口执行 I，依迁移计划补充跨平台检查；平台不具备时标为待外部验收。已知 NAT/DNS 环境失败按迁移计划逐项核对，不可把所有失败笼统归为历史问题。禁止关闭代理、修改全局网络或删除失败测试来制造通过。

### 2.2 交付报告

使用 [任务报告模板](task-reports/TEMPLATE.md)，每卡保存为 `docs/task-reports/TNN.md`。记录基线 SHA、变更、逐条验收、命令/退出码/结果、未验证项和剩余风险。截图或日志只保留必要脱敏内容，不提交身份私钥、token、凭据或业务文件。

报告与实现可同一提交，报告中的提交定位写“包含本报告的实现提交”，避免把自身最终 SHA 写入自身导致循环修改。提交推送后在回复中给完整 SHA、分支和远端结果；GPT 审核记录必须引用这个 SHA。

### 2.3 GPT 独立审核门槛

1. 获取准确的基线与候选 SHA，检查整个差异、调用方和相关现有测试，不只读工作 Agent 报告。
2. 对照卡中每条验收检查实际证据；关键复现独立执行，检查测试是否真的覆盖原故障和失败分支。
3. 检查兼容性、权限、资源释放、状态所有权和恢复语义；目录迁移也须检查 feature 与线格式变化。
4. 结论为“通过 / 需返修 / 阻塞”，写明问题位置与可验证的修正目标。通过范围只能覆盖已验内容。
5. 记录在 `docs/task-reports/TNN-review.md`，包含被审核 SHA。审核后新提交重新检查；阶段验收未通过不得把整个阶段标为完成。

代码审核通过但缺少真实平台/公网条件时，可明确记录“代码审核通过，外部验收待完成”；不允许据此解锁依赖该外部能力的发布任务。是否合并与是否对外发布分别判断。

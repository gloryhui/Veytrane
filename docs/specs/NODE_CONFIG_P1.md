# T08：P1 配置提交契约

- 状态：本轮实施规格冻结，测试后置。
- 路径：`src/tunnel/supervisor.rs`、`src/tunnel/rules.rs`、`src/admin/mod.rs`、`src/main.rs`、`src/storage/atomic.rs`。

## 最小模型

P1 暂由同一 AdminState 更新协调器串行所有 Web 和 SIGHUP 入口（无 Web 时也建立本地协调器，不启动 HTTP）；后续 T25 抽取正式 state/config 服务与 revision/恢复日志。有效配置对象与实际监听必须在同一个提交步骤发布。状态读取也获得更新锁，不观察半提交。SIGHUP 在获得该锁后读取候选文件。所有解析、校验、bind、持久化错误均记录同一 last_error，后续成功清除。

本轮不引入磁盘 schema、公开 revision 或跨资源 ACID 承诺。手工配置文件是候选：SIGHUP 失败时文件可能仍为无效候选，运行态及 API 保留有效旧配置；完整独立有效快照与启动恢复由 T25 交付。普通规则删除/改目标仅影响新流，已接纳流自然结束。

## 准备及提交

1. 获得协调锁；解析完整配置，验证 peer 不变、字段及重复项。Web 保留至少一条可在重启时定位 peer 的启用规则；本地 SIGHUP 允许空规则撤销全部授权，保持历史差异并明确来源。
2. supervisor 保留全部旧监听及目标，准备新监听但不创建接受任务；失败直接释放全部准备资源。端口交换、重用仍由其他旧规则占有的监听明确拒绝，建议先停用再修改。
3. Web 保存：随机唯一 create_new 临时文件，写入、同步后平台原子替换；Windows 使用 MoveFileExW 替换，不删除旧文件。替换前任何失败均保持旧配置、旧监听及旧文件。
4. 在已获取所有异步锁后，同一不含 await 的提交段激活新监听、通知旧监听停止新接入、更新旧监听目标及有效快照、清理错误。提交后仅等待旧监听任务退出，等待取消不回滚已提交状态。持有 supervisor 互斥锁，外部不得插入第二次 apply。
5. 文件已替换而目录同步失败：候选视为已提交，继续发布新运行态与快照，记录“已提交但持久化确认失败”并返回错误，不能回滚成旧权限或假称未提交。新启动按文件恢复；P1 不保证断电跨资源事务。

服务策略在准备阶段取得校验后的策略写锁，文件替换后切换策略不可失败；不先改策略再尝试写盘。不允许以“尝试 apply 旧配置”作为可靠回滚。

## 故障向量（均待后续执行）

| 场景 | 预期 |
| --- | --- |
| A/B→B/C，C 被占用 | 保持 A/B 监听及旧有效配置，API 报错 |
| 任意字段/peer/重复 ID 无效 | 保持旧状态，API 报错 |
| 文件替换前写盘失败 | 已准备监听释放，旧监听/文件/快照保持 |
| 同监听改目标 | 提交后新流使用新目标，旧流自然结束 |
| 成功增删、禁用 | 新监听仅提交后接纳，被删除者停止新接入 |
| 端口互换/其他规则占位 | 准备阶段拒绝，无监听被移除 |
| Web/SIGHUP 并发 | 同一锁串行；文件在获得锁后读取，无过期预读覆盖 |
| 失败后成功 | last_error 清空；API 与监听一致 |
| 替换后目录同步失败 | 新快照/运行态发布，显示提交后的持久化警告 |

T09 负责资源 prepare/commit；T10 负责共享协调器、持久化及入口状态。两者均不单凭编译关闭 BUG-02。

## 可重复命令

先构建对应旧基线和修复二进制。Windows 本轮旧二进制保存在 `target/node-baseline-bin/p2p_file.exe`；修复版为 `target/debug/p2p_file.exe`。以下命令全部实际运行，退出 0：

```powershell
python -X utf8 scripts/node-signal-loss-smoke.py --binary target/node-baseline-bin/p2p_file.exe --mode confirm-bug --path direct --output target/node-bug01-baseline
python -X utf8 scripts/node-signal-loss-smoke.py --binary target/node-baseline-bin/p2p_file.exe --mode confirm-bug --path relay --output target/node-bug01-relay-baseline
```

## 证据

| 实际路径 | 旧基线确认模式 | 修复验证模式 |
| --- | --- | --- |
| Direct | 停信令后首轮业务断开，后续成功样本 0；确认观察到旧缺陷 | 长流+40轮新请求全部成功；恢复信令后原流继续、原身份重新登记；重启客户端建立新会话成功 |
| Relay | 停 TCP 信令代理后首轮业务断开，样本 0 | 同样40轮、恢复及新会话全部成功；UDP Relay 后端在停信令期间保持运行 |

每轮先核对已认证 winner 的真实 `path_kind`；Relay 使用受控 Direct 黑洞。没有停止 Relay 后端来冒充“仅停止信令”。JSON 的 PASS 在 confirm-bug 中意为“确实观察到失败”，在 verify-fix 中意为“业务保持”，两者不能混用。所有操作有界等待，动态端口、临时新身份，进程由 Fixture 回收。Ubuntu 也通过 Direct 40轮验证。

日志/结果在上述输出目录；信令恢复/new_session 字段均由实际步骤得出。仅同机受控网络通过，真实双 NAT 停信令及公网重连仍需 R06/R10。

## 1. 交付原则

本计划服务于“老家 Ubuntu 无界面节点，同时供办公室 Mac 与家里 Windows 桌面端使用，阿里云负责信令”的实际场景，并保留点对点文件能力。

本次交付仅为设计文档。以下修复、重构、协议升级、部署和测试均是后续工作，不是本文已完成的事项。三个已复现缺陷必须被纳入跟踪，不能用架构重构代替缺陷关闭。

执行原则：

- 先建立回归与修复已知问题，再做行为保持的模块抽取，再统一协议和运行入口。
- 每阶段拆为可审查的小批次；目录迁移与协议变更尽量分开，避免一个提交同时改变编码、授权和文件发布。
- 每批次记录基线、目标 SHA、兼容影响、验证结果及回退方式。阶段完成由退出条件决定，不按提交数量或编译成功判定。
- 不在旧 CLI、桌面和新 Agent 三处重复实现业务功能。过渡适配必须有明确归属和退出条件。
- 本地复现、自动化回归、跨平台 CI、真实设备与公网验收分别记录；不得互相替代。

## 2. 已知缺陷清单

下列编号为本文本地跟踪编号，不表示已在 GitHub 创建新 Issue。相关现有实现来自 [Issue #85](https://github.com/gloryhui/p2p_file/issues/85)、[PR #86](https://github.com/gloryhui/p2p_file/pull/86) 和 [PR #87](https://github.com/gloryhui/p2p_file/pull/87)。

缺陷标题中的 P1/P2 表示问题优先级；“P1 修复任务”等正文中的 P0–P6 表示迁移阶段。三个缺陷均安排在迁移阶段 P1 处理。

### BUG-01 / P1：信令掉线关闭活跃 Direct 业务

- 位置：`src/tunnel/mod.rs` 的 `serve_session`，信令 `next_event()` 出错后退出服务循环，最终关闭 network/连接。
- 已复现：隔离运行 signal、serve、forward 和 TCP echo 服务，已建立业务流后只停止信令进程，业务流收到 `Connection reset by peer`。
- 期望：健康的已认证 Direct 连接继续服务；信令独立退避重连并使用同一身份重登。用户主动退出、身份切换和强撤销仍可关闭连接。
- P1 修复任务：将信令失联与业务会话关闭分离，管理 reader/reconnect 任务生命周期，禁止错误后空转和旧代回调覆盖新状态。
- 专项验收：持续传输及周期请求跨越信令停止/恢复均不因信令掉线中断；恢复后新 peer/新会话可建立；超时、显式退出和资源释放正确；Direct/Relay 原有行为回归。
- 后续归属：P2/P4 的统一 session 管理；信令错误不再由 tunnel 业务模块决定所有连接生死。

### BUG-02 / P2：SIGHUP 部分失败导致运行态与配置快照不一致

- 位置：`src/main.rs` 的客户端 SIGHUP 分支、`src/tunnel/supervisor.rs` 的 `apply`。
- 已复现：原有 A/B；候选删除 A、保留 B、新增 C，但 C 的端口被外部进程占用。应用后实际仅有 B 监听，管理 API 仍返回 A/B，`last_error=null`，A 连接被拒绝。
- 期望：本次更新失败时旧的已提交规则保持可用；API 和各界面准确报告有效配置、运行状态及错误。不能显示未运行的规则为已成功应用。
- P1 修复任务：先准备全部新增/替换资源再提交，失败释放候选、保留旧监听；让 SIGHUP 与 Web 共用更新协调和错误状态。不能准备的端口交换在提交前明确拒绝。
- 专项验收：占用端口、非法字段、持久化失败均不破坏 A/B；正在传输的业务保持；成功增删/改目标生效；Web 与 SIGHUP 并发更新不互相覆盖；API 错误状态可见并在后续成功后清除。
- 后续归属：P4 的配置 revision、提交记录和故障恢复。P1 不要求提前完成全部新存储格式，但不能只修页面显示而保留不可解释的部分应用。

### BUG-03 / P2：Web 增删行丢失未保存的其他行编辑

- 位置：`src/admin/index.html` 的新增/删除处理器在收集表单前重绘。
- 已复现：修改现有行名称及目标后点击“新增规则”，原行恢复为旧值。
- 期望：增删行保留其他行的当前草稿；保存成功才更新已提交状态，失败保留可继续编辑的草稿。
- P1 修复任务：统一草稿状态与输入事件，或在结构变更前完整收集表单；不要将草稿与服务端运行快照混为一份对象。
- 专项验收：服务端/客户端两种表单，修改文本、启用状态和自动启动字段后新增或删除其他行，草稿均保留；保存成功落盘、失败保留；删除自身时仅删除所选行。
- 后续归属：P5 的展示层草稿模型；此问题不需要等待协议统一。

## 3. 兼容范围与升级策略

### 3.1 需要独立验收的兼容面

| 兼容面 | 承诺与范围 | 明确不承诺 |
| --- | --- | --- |
| CLI 命令入口 | 在迁移期保留已有命令的参数含义、退出结果及文件策略；改为控制 Agent 时提供迁移说明 | 所有日志文本永久不变；供程序使用的输出应有独立版本契约 |
| 旧 CLI 线上协议 | 保留基线旧端 fixture 与显式兼容路径；新功能只在统一协议实现 | 自动获得桌面任务/目录/密码认证能力 |
| 旧桌面线上协议 | 保留 `P2PD`/远程认证的明确兼容模式与版本 fixture | 仅因共用 QUIC 就与旧 CLI 自动互通 |
| 新统一协议 | 所有新入口使用同一种节点会话和业务语义，按能力协商 | 只支持 TCP 的节点被迫开放文件或测速 |
| 身份与短 ID | 显式导入/复用原私钥以保留 NodeId；同一信令映射库保留短 ID | 生成新身份后仍拥有旧授权；更换或丢失信令库后短 ID 不变 |
| 配置和任务数据 | 支持已记录 schema 的显式导入/迁移，保留来源、备份和有效配置 | 任意旧二进制直接打开新 schema；凭空合并冲突身份/任务 |
| 文件行为 | 保留校验、持久 checkpoint、恢复和完成回执；原冲突策略显式迁移 | 默默将不覆盖改成覆盖，或将备份发布改成另一种策略 |
| 信令/Relay | 保留现有注册和 Relay 边界；本次统一不要求云端解密业务 | 仅更新云端即可让旧 CLI 和旧桌面业务互通 |

### 3.2 连接组合

| 两端组合 | 基线状态 | 迁移后要求 |
| --- | --- | --- |
| 旧 CLI ↔ 旧 CLI | 现有 CLI 能力 | 保持原回归和既有授权边界 |
| 旧桌面 ↔ 旧桌面 | 现有桌面能力 | 保持原回归、密码/可信设备及方向授权 |
| 旧 CLI ↔ 旧桌面 | 无统一业务互通 | 不宣称原地兼容；至少一端需升级或显式适配 |
| 新节点 ↔ 新节点 | 尚未实现 | GUI/CLI/无界面入口任意组合，按能力和权限互通 |
| 新节点 ↔ 旧 CLI | 尚未实现 | 显式 legacy CLI 模式、精确 NodeId/资源白名单，仅支持旧能力 |
| 新节点 ↔ 旧桌面 | 尚未实现 | 显式旧桌面适配，保留旧认证与能力语义 |

模式在已知 peer 配置/受控入口中明确选择，不把“协商失败后逐个尝试旧协议”作为正常策略。身份握手、QUIC 发起角色、首流格式和授权路径都必须纳入兼容测试，不能只比消息结构。兼容流量由单 Agent 统一分发，不能产生第二个同身份信令登记。

若特定旧端组合无法在单所有者模型中安全区分，必须明确标为不支持并要求升级；不得降低认证或隐式使用另一身份让测试通过。P3 退出前，承诺支持的旧端组合必须有实际 fixture 证据。

### 3.3 数据导入、升级与回退

1. 盘点桌面设置、CLI service/client JSON、私钥位置、信令映射库、任务记录及未完成接收目录；先输出导入预览和冲突。
2. 相同身份只生成一个节点配置；不同身份分别保留为不同实例。相同监听端口、规则 ID 或接收策略发生冲突时拒绝隐式覆盖，要求明确选择。
3. 迁移使用备份、目标 schema 版本和迁移记录。未知 schema、损坏配置和未识别凭据保持原文件并报错。
4. 数据目录先获得实例锁，确认旧进程已停止再移交；新旧进程不得同时操作任务库或用同一身份登记。
5. 启动新 Agent 后检查 NodeId、信任来源、规则、监听、任务和接收文件。验证成功前不清理原备份。
6. 尚未发生新写入时可停止新 Agent，按记录恢复旧配置/二进制。发生新任务、文件发布或授权撤销后，回退需先核对新数据及当前安全策略；不能用旧备份复活已撤销授权，也不能删除新接收文件。

旧协议和旧命令不在本计划中直接删除。退役条件为：四设备场景全部升级、兼容使用清单完成核对、升级/回退说明交付、互通和数据验收通过、发布说明明确退役版本。具体版本窗口在发布阶段确定，不用未经验证的日期承诺代替。

## 4. 分阶段实施

### P0：冻结边界与验证基线

**输入**：当前 main、本文与目标架构、既有 ADR 和三项复现。

**交付物**：模块依赖清单、协议/持久化版本清单、旧端 fixture、可重复的隔离复现脚本、支持范围与测试环境说明。复现脚本使用独立身份、临时目录和 loopback 端口，清理自己创建的进程。

**退出条件**：BUG-01/02/03 在基线上可复现；现有身份、文件完成、续传和授权测试可执行；基线失败与环境限制明确记录；每项后续工作有对应验收编号。

**回退**：仅验证材料，无生产数据迁移。

### P1：修复三项已知缺陷

**依赖**：P0。三个修复分别交付，避免绑定到大型重构。

**交付物**：BUG-01 信令生命周期修复、BUG-02 一致的规则应用/错误状态、BUG-03 表单草稿修复，以及对应回归。

**退出条件**：第 2 节专项验收全部通过；默认及 GUI 相关测试、格式和静态检查完成；Web 有实际浏览器交互证据；现有文件/转发/测速协议字节和授权要求未被修改。

**回退**：使用上一可用二进制/源版本；不引入新数据格式。不得以回退到已知断流版本作为稳定性修复的最终交付。

### P2：抽取共享核心，保持线上行为

**依赖**：P1。先迁移依赖，再迁移入口。

建议批次：

1. 抽取身份授权、规则、任务模型、错误和存储；将无界面所需依赖从 `gui` 中分离。
2. 抽取文件服务、恢复、限速、空间预算和发布策略，保留旧文件策略适配。
3. 抽取 session、多 peer 和网络编排；TCP 模块不再负责文件/测速总分发。
4. 建立核心命令、快照和事件接口；桌面暂以内嵌方式调用，GUI 保留呈现和平台交互。

**交付物**：无 GUI 核心、明确的旧协议适配层、行为等价测试及模块依赖说明。此阶段不改变 magic、版本或 postcard 变体序号。

**退出条件**：Linux 无图形依赖可构建/运行核心测试；原桌面功能回归；旧端线格式 golden 测试和数据恢复通过；核心不反向引用 GPUI/窗口/CLI 输出；同一业务状态机只有一个维护位置。

**回退**：逐批回退源变更，保持数据 schema；抽取提交与功能提交分离便于定位。

### P3：统一节点协议与兼容适配

**依赖**：P2。

**交付物**：统一协议编码规范、最小基础能力与可选能力、统一文件/隧道/测速分发、受授权服务目录、旧 CLI/桌面适配器、版本与能力错误契约。

**退出条件**：

- 同一文件任务可由 CLI 或 GUI 创建，使用相同核心和统一线上流程；headless peer 不要求图形依赖。
- 最小 TCP 节点可连接；关闭文件服务时明确拒绝文件业务而不影响 TCP。
- 新节点互通及第 3 节承诺的旧端组合通过；未知版本/格式、错误凭据、缺失安全能力明确拒绝，无认证降级。
- 文件完成、暂停/续传、任务绑定、重放、丢回执、重名策略和损坏帧验证通过。
- 服务目录仅返回授权资源；改目标或撤销后开流重新验证，缓存目录不能绕过。

**回退**：冻结新数据写入、停止节点后按 schema/任务记录选择可读版本；保留旧适配模式，不将新任务直接交给不识别它的旧端。

### P4：无界面 Agent、多对端与统一配置服务

**依赖**：P2 控制接口稳定、P3 互通达标。

**交付物**：前台 Agent 宿主、实例锁、本地 IPC、统一配置更新服务、headless 凭据/可信设备管理、systemd 示例、多客户端会话和状态诊断。

**退出条件**：

- 一个 Ubuntu Agent、同一身份同时服务 macOS 和 Windows 对应的两个 peer；至少各两条转发互不踢下线。
- 实例锁覆盖 GUI/CLI/Agent 的重复启动；同数据目录或同身份启动冲突可诊断。
- 目标离线仍可打开本地管理界面、修改规则并查询等待原因。
- GUI/CLI/Web/SIGHUP 同用配置协调器；revision 冲突、端口冲突、磁盘失败、提交阶段进程终止有确定恢复结果。
- 普通服务撤销与强撤销分别按架构语义执行；重新连接不能复用已撤销 grant。
- 信令失联不关闭健康业务连接；恢复后能够重新登记、配对和接受新请求。

**回退**：暂停新接入，检查持久状态和安全变更，停止新 Agent 再交回旧宿主；禁止双宿主并跑。systemd 单元切换记录运行用户、路径和实际二进制版本。

### P5：桌面、CLI、Web 统一管理入口

**依赖**：P4。

**交付物**：桌面通过管理接口附着用户 Agent；CLI 管理命令与旧命令适配；Web 管理适配；配置导入工具；三平台安装/启动/升级说明。确切命令名在此阶段正式发布，不将设计示例当作可执行命令。

**退出条件**：

- GUI 不启动第二套网络会话、不直写任务/核心配置；打开多个入口看到相同 revision 和实际运行状态。
- UI 关闭/崩溃后任务按后台策略继续，重新打开从快照与事件恢复；显式停止 Agent 可收尾。
- 老家发布授权服务后，Mac/Windows 界面可查询、选择、新建、启停转发，不需反复修改老家启动参数。
- 新增未授权目标仍需老家管理员授权；客户端没有因连接成功获得远程配置管理权。
- 两种 Web 表单及原生界面增删行保留草稿；保存失败可继续修改，外部配置更新有冲突提示。
- 旧命令/旧配置导入保留身份和文件策略；常用机器可升级后回退，不遗留争用端口的后台进程。

**回退**：回退前端时检查本地 API 版本；版本不兼容明确拒绝，不能绕过 Agent 直接启动旧内嵌核心访问同一数据目录。

### P6：四设备真实验收、发布和清理

**依赖**：P1–P5 退出条件满足。

**交付物**：四设备运行记录、真实双 NAT/IPv6/Relay 证据、原生 GUI 验收、打包/安装/重启验证、升级回退说明、兼容矩阵和剩余限制。

**退出条件**：第 5 节所有适用的必验项通过；外部环境未完成的项目保持待验，不能以 CI 打包通过关闭；清理重复模块和历史说明只在所有调用方迁移完成之后进行。

**回退**：按实际部署批次逐台回退，保留身份、任务和文件；信令/Relay 不因节点升级被无谓替换。旧适配器删除需要另一个明确的发布决策。

## 5. 验收矩阵

### 5.1 自动化与跨平台门禁

### 5.2 四设备实测

| 编号 | 操作 | 通过标准 |
| --- | --- | --- |
| R01 | 老家 Ubuntu 重启 | Agent 无图形登录即可启动，身份/配置正确，Mac/Windows 能重新连接 |
| R02 | Mac、Windows 同时连接老家 | 每端至少两条规则、同一老家身份，两端可并发访问，改变一条不影响另一端 |
| R03 | 在桌面添加转发 | 从老家授权目录选服务、设置本机端口、保存后访问成功；目标地址按老家网络解释 |
| R04 | 真实 HTTP 与流式 API | 首页、静态资源、API、流式响应均成功；使用可控测试请求核对完整响应；长连接不因管理界面操作中断 |
| R05 | 空闲恢复 | 关闭外部保活/自动重启看护；记录实际 idle/re-punch 参数，空闲超过两者周期后两端新浏览器/API 请求自动恢复，无需重启 CLI/Agent |
| R06 | 信令停止/恢复 | 已建立 Direct 业务持续传输；恢复后登记、新连接正常；用 PID/日志证明非外部看护重启 |
| R07 | 老家重启与短断网 | 旧 TCP 会话结束可解释，后续请求自动重新配对认证；文件按既定恢复策略继续，无假完成 |
| R08 | 撤销权限 | 撤销某服务阻止新流；强撤销设备立即失效其授权；未受影响设备继续工作 |
| R09 | 文件互通 | Mac↔Ubuntu、Windows↔Ubuntu、Mac↔Windows 在开启相应权限时传输文件/目录，续传和完成 hash 正确 |
| R10 | 路径与 Relay | 记录实际获胜地址族和 Direct/Relay；Relay 使用明确配置，在受控直连失败时验证，不能凭“已开启”判断实际使用 |
| R11 | 原生后台与升级 | Mac/Windows 关闭窗口后按策略继续；登录启动、重新打开、升级、回退及停止服务无重复身份或残留进程 |
| R12 | 管理失败 | 实际制造端口占用/非法配置/保存失败，旧服务可用，所有入口呈现一致错误和实际监听 |

R05/R07 必须在独立真实网络中验证；单机 loopback 不算真实双 NAT。IPv6 或 Relay 部署条件缺失时标记未验及原因，不伪造路径证据。CI 产物存在不等于安装、系统服务运行或原生交互通过。

### 5.3 证据格式与关闭条件

每次验收记录：编号、日期与时区、代码 SHA/构建标识、OS/架构、脱敏拓扑、节点角色、有效配置版本、操作步骤、预期/实际结果、相关日志/截图、进程退出与资源回收、结论和剩余限制。

协议兼容证据同时记录双方二进制/协议版本；文件证据包含测试文件大小、hash 和发布/恢复结果；联网证据包含实际获胜路径与身份认证结果。不得记录私钥、密码、管理 token 或不必要的业务数据。

阶段状态使用“待实施 / 实施中 / 待外部验收 / 已验收”。未做的验证保持未完成，不把“设计覆盖”当作“功能完成”。BUG-01/02/03 独立关闭；Issue #85 的外部验收只在相应证据补齐后再评估关闭。
